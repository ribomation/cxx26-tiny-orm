# Finding 03 — What the second backend found

*Recorded 2026-09-14 · PostgreSQL 18.6 via libpq, SQLite 3.46.1*

SQLite was added for one reason: an interface with a single implementation is
unverified. You cannot tell, by looking, whether a `dialect` abstracts the
things that actually differ or merely the things you happened to think of.

This note records what the second implementation found that inspection did not.

## The bug

The demo loads OpenFlights data into whichever database its URL names. It had
been working against PostgreSQL for a while. The first run against SQLite died
on the first statement:

```
failed: tiny-orm: near "CASCADE": syntax error
        [sql: DROP TABLE IF EXISTS "routes" CASCADE;]
```

**SQLite has no `DROP TABLE ... CASCADE`.** PostgreSQL uses it to drop dependent
constraints along with the table, and the loader relied on it to drop four
tables joined by foreign keys without ordering them by hand.

The dialect gained a method, and `drop_table_sql` stopped emitting the keyword
where it is not accepted:

```cpp
/// Whether DROP TABLE accepts CASCADE.
[[nodiscard]] virtual bool supports_drop_cascade() const = 0;
```

Omitting rather than failing is safe here because the engines that lack the
keyword also do not need it: SQLite drops a table's constraints with the table.

## Predicted versus discovered

The dialect interface was designed by listing what differs between engines,
before either backend existed. That list was mostly right and materially
incomplete.

| Difference | How it was found |
|---|---|
| Placeholders — `$1` vs `?` | predicted |
| Identifier quoting | predicted |
| Type rendering — `DOUBLE PRECISION` vs `REAL`, `BOOLEAN` vs `INTEGER` | predicted |
| Identity clause — `GENERATED BY DEFAULT AS IDENTITY` vs nothing | predicted |
| `RETURNING` support | predicted |
| Raw type override being integral | predicted |
| `LIMIT` / `OFFSET` | predicted — and **wrong**: they are identical |
| **Bind-parameter limit — 65535 vs 32766** | **discovered, building bulk insert** |
| **`DROP TABLE ... CASCADE`** | **discovered, running the demo** |
| **How a bound boolean is stored** | **discovered, reading the demo's output** |

Three of ten were missed, and one predicted difference turned out not to be one.

What separates the two columns is not difficulty. It is that the predicted rows
were found by comparing *syntax* across documentation, and the discovered rows
were found by *doing something new*: sending more parameters than a statement
may carry, and dropping tables joined by foreign keys. Neither shows up when you
sit down and list how two dialects differ.

## The third one, which no error reported at all

The first two discoveries announced themselves — a syntax error and a parameter
limit. The third did not.

The demo prints four report sections. Against PostgreSQL all four filled.
Against SQLite, *Airlines by route count* came back empty, and nothing anywhere
said why. The query is ordinary:

```sql
SELECT al.name, al.country, count(*) AS routes
FROM routes r JOIN airlines al ON al.id = r.airline_id
WHERE al.active
GROUP BY al.name, al.country
```

Parameters are bound as text, and `to_param(bool)` rendered `"true"`. That is
fine for PostgreSQL, which coerces the text into a `BOOLEAN` column. SQLite does
not coerce: the column has INTEGER affinity, `"true"` is not convertible to an
integer, so it is **stored as text** — and `WHERE al.active` then evaluates a
non-numeric string as false, for every row.

```sql
CREATE TABLE t (active INTEGER NOT NULL);
INSERT INTO t VALUES ('true'), ('1');

SELECT active, typeof(active) FROM t;   -- true|text
                                        -- 1|integer
SELECT count(*) FROM t WHERE active;    -- 1, not 2
```

What makes it worth its own section is that the round trip *through the
framework* was fine the whole time: `from_cell<bool>` accepts `"true"`, so
`load()` returned the right value and every test passed. Only the engine's own
reading of the column was wrong. The fix is one line — bind `"1"`/`"0"`, which
both engines read as a boolean — and the regression test asserts the thing that
actually broke, `WHERE "active"` in raw SQL, rather than the round trip that
never did.

Column affinity is not in anybody's list of dialect differences, because it is
not a difference in *syntax*. It is a difference in what the engine does with a
value after it has accepted it.

## The identity clause, which nearly hid a second bug

SQLite's `identity_clause()` returns the empty string, and the reason is worth
recording because "SQLite's keyword is `AUTOINCREMENT`" is the obvious and wrong
answer.

A column declared exactly `INTEGER PRIMARY KEY` is an alias for the rowid and
already generates keys. `AUTOINCREMENT` only suppresses rowid reuse, costs an
extra internal table, and is rejected anywhere else — including on a
`PRIMARY KEY (...)` table constraint, which is the form this framework emits.
Emitting nothing is both simpler and more widely valid.

Verified by the integration tests, which insert 2500 rows on both engines and
check the generated keys come back ascending and in `VALUES` order.

## A coda: what the data found

The same lesson holds one level down. `from_cell<bool>` accepted `t`, `true` and
`1` — PostgreSQL's and SQLite's own output — which is exactly the set you arrive
at by thinking about what a *database* returns.

Then `airlines.dat` turned out to write `Y` and `N`, and every airline silently
loaded as inactive. CSV producers are not databases and have no shared
convention; the accepted set is now `t/true/1/y/yes`, case-insensitively.

Invented input agrees with whatever you invented. Real input does not.
[Finding 04](findings-04-importing-real-data.md) collects the rest of what the
real files had to say.

## The rule

> An abstraction with one implementation is a guess. The second implementation is
> the test, and it should be built while the first is still small enough to change.

Two backends is the minimum that proves anything. It is also, for an experiment
this size, the maximum worth building: a third would have found less than the
second, and the second was cheap only because the interface was still seven
methods long when it arrived.
